# Contributing

Contributions are welcome, especially field-specific modules that help reviewers reason from the real task and its bottlenecks rather than from a field's promotional vocabulary.

## Good module contributions

A useful domain module should:

1. Define the field's core tasks, users, and relevant system boundaries.
2. Explain the mechanisms and bottlenecks that determine task-level performance.
3. Identify strong competing approaches and explain when each is appropriate.
4. Map laboratory metrics to system outcomes, including failure, scale-up, maintenance, and cost where relevant.
5. Name reliable source routes and explain which sources can establish which facts.
6. Identify recurring comparison errors, misleading benchmarks, and common promotional overreach.
7. State what evidence could strengthen, weaken, or reverse a decision.
8. Include examples only when their facts and source boundaries can be checked.

Start from [`assets/domain-module-template.md`](assets/domain-module-template.md). Keep claims testable, distinguish field consensus from disputed views, and cite primary or authoritative sources where possible. Do not turn one case, one team's experience, or a contributor's preference into a universal rule.

## Review expectations

Please include:

- the module's intended domain and limits;
- sources and the claims they support;
- any known disagreements or alternative explanations;
- one or more examples of how the module changes the analysis of a real task;
- a note on potential conflicts of interest or close involvement in the technology, where relevant.

The skill's core report schema should not be changed casually. If a contribution proposes schema changes, explain the migration path and update all affected documentation.
